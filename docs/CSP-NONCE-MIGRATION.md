# CSP `unsafe-inline` to Nonce-Based Migration Plan

> Status: Planned | Owner: @xiyijixiyifula | Effort: 4-6 hours | Priority: MEDIUM (XSS hardening)
>
> Related: [audit finding DES-02](../audit-report-polis-20260615.md) | [known issue](../KNOWN-ISSUES.md) | [bug timeline 2026-06-09](../bugs/timeline/2026.md)

## 1. Current State

**File: `web/next.config.js:38-71`** — CSP headers are set via the `headers()` config function:

```js
// script-src: Next.js requires unsafe-inline for client-side hydration scripts.
// Long-term: migrate to nonce-based CSP via Next.js generateCsp or middleware.
const scriptSrc = isDev
  ? "'self' 'unsafe-eval' 'unsafe-inline'"
  : "'self' 'unsafe-inline'";
const csp = [
  "default-src 'self'",
  `script-src ${scriptSrc}`,
  "style-src 'self' 'unsafe-inline'",
  "img-src 'self' data: https:",
  "connect-src 'self' https:",
  "font-src 'self'",
  "frame-ancestors 'none'",
  "form-action 'self'",
  "base-uri 'self'",
].join('; ');
```

### Why `unsafe-inline` Is Currently Required

Next.js injects inline `<script>` tags into the HTML for client-side hydration. These inline scripts are generated by the framework at build time and appear as:

```html
<script>self.__next_f.push([1,"...chunk data..."])</script>
<script src="/_next/static/chunks/main-abc123.js"></script>
```

Without `unsafe-inline` in `script-src`, browsers block these hydration scripts. The result: **all client-side pages render as blank white screens**. This regression was encountered on 2026-06-09 when CSP was tightened — see [bug timeline](../bugs/timeline/2026.md#2026-06-09).

### Current Risk

- `unsafe-inline` allows ANY inline script to execute
- If an attacker manages to inject inline `<script>` tags (e.g., via a stored XSS that bypasses DOMPurify), CSP will not block it
- This weakens the defense-in-depth provided by CSP

## 2. Target State

Replace `'unsafe-inline'` with `'nonce-{random}'` in both `script-src` and `style-src` directives:

```
script-src 'self' 'nonce-{random-value}';
style-src 'self' 'nonce-{random-value}';
```

### How Nonce-Based CSP Works

1. Each HTTP response gets a unique, cryptographically random nonce
2. The CSP header includes `script-src 'nonce-{value}'`
3. Every `<script>` tag that should be allowed (framework chunks, inline hydration scripts) carries `nonce="{value}"`
4. Any injected `<script>` without the matching nonce is blocked by the browser
5. Attackers cannot predict the nonce (it changes per request), so injected scripts are effectively blocked

### Limitations of Nonce in Next.js

| Limitation | Impact |
|---|---|
| **Static pre-rendering ISR/SSG** — nonces break CDN caching | Must use `Cache-Control: private` or switch to SSR-only for nonced pages |
| **Streaming SSR** — nonce must be known before the first chunk is flushed | Must generate nonce early in the request lifecycle |
| **Third-party scripts** (Google Analytics, etc.) — cannot predict the nonce | Must either: (a) use `strict-dynamic`, (b) use hash-based allowlist alongside nonce, or (c) load third-party scripts via Next.js `<Script>` with `strategy="afterInteractive"` |
| **`<style jsx>` / CSS-in-JS** — some libraries inject `<style>` tags that need the nonce | Must pass nonce to the CSS-in-JS provider |

## 3. Implementation Steps

### Step 3a: Create `middleware.ts` with Per-Request Nonce Generation

**New file: `web/src/middleware.ts`**

```typescript
import { NextRequest, NextResponse } from 'next/server';

export function middleware(request: NextRequest) {
  // Generate a cryptographically random nonce
  const nonce = crypto.randomUUID().replace(/-/g, '');

  // Build CSP with nonce
  const isDev = process.env.NODE_ENV !== 'production';
  const scriptSrc = isDev
    ? `'self' 'unsafe-eval' 'nonce-${nonce}'`
    : `'self' 'nonce-${nonce}'`;

  const csp = [
    "default-src 'self'",
    `script-src ${scriptSrc}`,
    `style-src 'self' 'nonce-${nonce}'`, // also remove unsafe-inline from style
    "img-src 'self' data: https:",
    "connect-src 'self' https:",
    "font-src 'self'",
    "frame-ancestors 'none'",
    "form-action 'self'",
    "base-uri 'self'",
  ].join('; ');

  const requestHeaders = new Headers(request.headers);
  // Store nonce for downstream consumption (e.g., in layout.tsx)
  requestHeaders.set('x-nonce', nonce);

  const response = NextResponse.next({
    request: { headers: requestHeaders },
  });

  response.headers.set('Content-Security-Policy', csp);
  response.headers.set('X-Frame-Options', 'DENY');
  response.headers.set('X-Content-Type-Options', 'nosniff');
  response.headers.set('Referrer-Policy', 'strict-origin-when-cross-origin');
  response.headers.set('Permissions-Policy', 'camera=(), microphone=(), geolocation=(), interest-cohort=()');
  response.headers.set('Cross-Origin-Resource-Policy', 'same-origin');

  return response;
}

export const config = {
  // Apply to all routes except static assets and API routes
  matcher: ['/((?!_next/static|_next/image|favicon.ico|api/).*)'],
};
```

**Key design decision**: Using `crypto.randomUUID()` (available in Node.js 19+, Next.js runtime) instead of `Math.random()` to guarantee cryptographic randomness.

### Step 3b: Pass Nonce to Next.js Internals via `_document.tsx`

To ensure Next.js attaches the nonce to all framework-generated `<script>` tags (hydration chunks, `next/script`, inline scripts), we override `_document.tsx`.

**If `web/src/pages/_document.tsx` exists, update it. Otherwise, create it:**

```typescript
// This file ONLY applies to pages/ directory (Pages Router).
// For App Router (app/), see Step 3c below.
```

**Note for App Router**: Next.js App Router (used by Polis) does not support `_document.tsx`. Instead, nonce propagation requires a **root layout** that reads the nonce from headers.

### Step 3c: Pass Nonce via Root Layout (App Router Approach)

**Modify: `web/src/app/layout.tsx`**

```typescript
import { headers } from 'next/headers';
import Script from 'next/script';

export default async function RootLayout({ children }: { children: React.ReactNode }) {
  // Read nonce set by middleware
  const headersList = await headers();
  const nonce = headersList.get('x-nonce') ?? '';

  return (
    <html lang="zh-CN">
      <head>
        {/* Pass nonce to all Next.js inline scripts */}
        <Script id="nonce-forwarder" strategy="beforeInteractive">
          {`window.__NONCE__ = '${nonce}';`}
        </Script>
      </head>
      <body>{children}</body>
    </html>
  );
}
```

**⚠️ Warning**: The approach above has a chicken-and-egg problem — `headers()` in layout requires the nonce to be available, but the nonce is set in middleware. In practice with Next.js App Router, middleware runs before layout rendering, so `headers()` can read `x-nonce`. However, the `Script` with `beforeInteractive` strategy itself generates a `<script>` tag that needs the nonce — meaning this approach may still produce a CSP error for the very first inline script.

**Alternative (more robust): Use `NextScript` from `next/document`**

For the Pages Router, this is straightforward. For App Router, the most reliable approach is to:

1. Let middleware set the CSP header (with nonce)
2. Use `next/script` with the `nonce` prop on any manually added scripts
3. For Next.js internal hydration scripts, configure `next.config.js` to pass the nonce

### Step 3d: Remove `unsafe-inline` from `next.config.js`

Once middleware handles CSP, remove the CSP section from `web/next.config.js` to avoid duplicate/inconsistent headers. The middleware response header takes precedence, but it's cleaner to have a single source of truth.

**File: `web/next.config.js`** — remove lines 38-71 (the `headers()` function), or comment it out with a note pointing to `middleware.ts`.

### Step 3e: Handle Dynamic Script Loading

The Polis frontend uses dynamic imports for the cherry-markdown editor:

```typescript
// web/src/components/CherryEditor.tsx (or similar)
const CherryEditor = dynamic(() => import('./CherryEditorImpl'), { ssr: false });
```

Dynamic imports via Webpack's code splitting do NOT use inline scripts — they create `<script src="...">` elements pointing to chunk files. Since our CSP allows `'self'` (which covers same-origin scripts), these are unaffected by the nonce change.

**However**: if any code uses `eval()`, `new Function()`, or inline event handlers (`onclick="..."`), these will break. Audit before proceeding:

```bash
grep -rn "eval(" web/src/
grep -rn "new Function" web/src/
grep -rn "on[a-z]+\s*=\s*\"" web/src/
```

**Findings as of 2026-06-15**: Zero `eval()` calls in frontend source. Zero inline event handlers. `unsafe-eval` is only enabled in dev mode for React DevTools hot reloading, not in production.

## 4. Risk Assessment

### Critical Risks

| # | Risk | Likelihood | Impact | Mitigation |
|---|------|-----------|--------|------------|
| R1 | Next.js hydration inline scripts don't carry the nonce, causing blank pages (same regression as 2026-06-09) | **HIGH** | **CRITICAL** — all pages blank | Test on staging first. Have a rollback plan: revert to `unsafe-inline` by commenting out middleware CSP and restoring `next.config.js` headers |
| R2 | Streaming SSR pages (if any) flush chunks before CSP header, causing a brief window with no CSP | **LOW** | **MEDIUM** — CSP only active after header is received | Not applicable — Polis does not use streaming SSR |
| R3 | CDN/proxy caches responses with stale nonces | **MEDIUM** | **MEDIUM** — cached pages would have nonces that don't match scripts on subsequent requests | Set `Cache-Control: private` on HTML responses. SPA pages (most of Polis) do not cache HTML anyway |
| R4 | Build-time inline scripts (SSG) cannot have per-request nonces | **LOW** | **LOW** — SSG pages would show CSP errors | Polis pages are primarily CSR/SSR, not SSG. If any page is SSG, convert to ISR with `revalidate` or accept `unsafe-inline` on those specific pages |

### Medium Risks

| # | Risk | Likelihood | Impact | Mitigation |
|---|------|-----------|--------|------------|
| R5 | `style-src 'nonce-*'` breaks `<style jsx>` or CSS-in-JS libraries | **MEDIUM** | **HIGH** — styles disappear | Verify all CSS-in-JS usage. Polis primarily uses Tailwind CSS (utility classes, no inline `<style>` injection) + CSS Modules. Risk is low in practice |
| R6 | Third-party integrations (Google Analytics, Vercel Analytics, etc.) fail to load their inline tracking scripts | **LOW** — Polis has minimal third-party scripts | **LOW** — analytics and search features break | Use `strict-dynamic` alongside nonce to allow scripts loaded by already-allowed scripts |
| R7 | CSP header set by both `next.config.js` AND middleware, causing conflicts | **MEDIUM** | **MEDIUM** — inconsistent behavior between routes | Remove CSP from `next.config.js` entirely when middleware is in place |

### Regression Risk: CSP Blank Page (2026-06-09 Pattern)

The same root cause (CSP blocking Next.js hydration) has already caused a production outage once. The nonce approach is the correct long-term fix, but the implementation must be verified in a real browser before deploying. The key difference: with nonce-based CSP, Next.js is supposed to attach the nonce to its own scripts. If it does not (version-specific behavior), pages will still be blank.

**Required pre-deploy verification**: See Section 6 (Testing Plan).

## 5. Phased Rollout Strategy

### Phase A: Nonce in Report-Only Mode (Safe)

Deploy CSP headers in **report-only** mode first:

```
Content-Security-Policy-Report-Only: script-src 'self' 'nonce-...'; report-uri /api/csp-report
```

This lets us collect violation reports without actually blocking anything. After 1-2 weeks of zero unexpected violations, proceed to Phase B.

**Effort**: 1-2 hours | **Risk**: None (report-only is non-blocking)

### Phase B: Nonce Enforcement + `unsafe-inline` Fallback (Conservative)

Use both `'nonce-*'` AND `'unsafe-inline'` simultaneously:

```
script-src 'self' 'nonce-{value}' 'unsafe-inline';
```

Since CSP allows any matching source, the presence of `unsafe-inline` means the nonce provides no real security benefit — but this stage validates that:

1. Nonce generation works per-request
2. Nonce is propagated to scripts correctly
3. No CSP violations appear in console for legit scripts

**Effort**: 1-2 hours | **Risk**: Minimal (unsafe-inline is still the safety net)

### Phase C: Remove `unsafe-inline` (Target State)

After Phase B confirms zero CSP violations:

```
script-src 'self' 'nonce-{value}';
```

**Effort**: 30 minutes | **Risk**: The real deployment risk — must pass the testing plan
